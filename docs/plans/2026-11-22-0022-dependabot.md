# Dependabot version updates

## Goal

Have Dependabot open PRs for new versions of the Go modules and GitHub
Actions that the repository uses, holding each new version back until it's
at least 14 days old, so that updates follow the rule in `AGENTS.md` without
anyone having to check release dates.

Left for later PRs: an entry for npm (with the SvelteKit scaffold), for
Docker (with the Dockerfile) and for Terraform (in M1, once the configuration
has a committed lock file). Each of those PRs adds its own entry, so that
Dependabot never watches something that doesn't exist yet.

## Design

### `.github/dependabot.yml`

Modelled on diary's, with the two ecosystems that exist so far:

```yaml
# Dependabot version updates. Security updates are configured separately in
# the repository settings, and aren't affected by the options below.
version: 2

updates:
  - package-ecosystem: gomod
    directory: /
    schedule:
      interval: monthly
    cooldown:
      default-days: 14
    groups:
      go:
        update-types: [minor, patch]

  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: monthly
    cooldown:
      default-days: 14
    groups:
      actions:
        update-types: [minor, patch]
```

- **Cooldown of 14 days** (`default-days`) for every update type. GitHub's
  docs say that a version inside its cooldown isn't considered for an update
  at all, and that the cooldown doesn't apply to security updates, so a fix
  for a vulnerability isn't held back.
- **Monthly**, as in diary: frequent enough for a small app, without a stream
  of PRs. A version is at least 14 days old by the time it's proposed, so a
  monthly check means that new versions arrive 14 to about 45 days after
  their release.
  - Rejected: weekly, which would mean more PRs to merge for little benefit.
- **Minor and patch updates grouped per ecosystem**, so that there's usually
  one PR per ecosystem a month. Major updates get their own PRs, because
  they're the ones that can need code changes.
- **GitHub Actions pinned by SHA:** Dependabot is expected to update both the
  SHA and the version comment after it (`# v7.0.1`), so that the pins from
  the CI PR stay readable. GitHub's docs that I could read don't say so
  explicitly, so the first Dependabot PR for an action will show it (see
  "Risks").

### What Dependabot doesn't update

- **The golangci-lint version** in the `lint` job's `version` input (and in
  the README) isn't a dependency that Dependabot knows about. It stays a
  manual update, as in diary.
- **The Go version** (the `go` directive in `go.mod`) is raised by hand when
  a change needs a newer Go, rather than relying on Dependabot.

## Risks

- **The configuration is invalid, so Dependabot silently does nothing:**
  GitHub only checks `dependabot.yml` once it's on the default branch, so no
  check on this PR catches it. After merging, the Dependabot tab of the
  dependency graph (Insights → Dependency graph → Dependabot) shows whether
  each ecosystem was checked, or the error. I'll put this in the PR's "For
  you" checklist.
- **A version less than 14 days old is proposed anyway:** only if the
  cooldown doesn't work as documented. No check catches it, but each
  Dependabot PR links to the new version's release notes, which show when it
  was released.
- **Dependabot updates an action's SHA but leaves the old version in its
  comment**, so the comment would be wrong: visible in the diff of the first
  Dependabot PR for an action. If it happens, the comments can be fixed by
  hand, or the pins changed back to tags.
- **A grouped update breaks something:** CI runs on Dependabot's PRs like on
  any other.

## Close review

- **`.github/dependabot.yml`:** whether it's valid is only checked after
  merging (see "Risks"), and a mistake there means updates silently stop.
  The rest of the configuration (schedule, groups) is easy to change and
  does little harm if it's wrong.
