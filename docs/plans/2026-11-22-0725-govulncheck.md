# govulncheck in CI

For lafeingcrokodil/flashcards#43.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

Run [`govulncheck`](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck) on
every pull request, on every push to `main`, and on a schedule, so that a
known vulnerability in code the app actually calls fails the checks. That
includes vulnerabilities in the standard library that a newer Go fixes, which
Dependabot doesn't cover.

Left for later: opening an issue when the scheduled run finds something (see
"Design"), which can reuse whatever lafeingcrokodil/flashcards#44 builds.

## Design

### Installing govulncheck: a Go tool dependency

`govulncheck` v1.9.0 (published 2026-10-11) is added to `go.mod` with
`go get -tool golang.org/x/vuln/cmd/govulncheck@v1.9.0`, and run with
`go tool govulncheck ./...`. Tried in a scratch copy of the repository:

- `go.mod` gets a `tool golang.org/x/vuln/cmd/govulncheck` line and
  `golang.org/x/vuln v1.9.0 // indirect` in its `require` block, along with
  five other `golang.org/x/...` modules that `x/vuln` needs (`mod`, `sync`,
  `sys`, `telemetry`, `tools`), all published between 2026-09-23 and
  2026-10-10.
- The app's own imports don't change, so `depguard` and the binary are
  unaffected: tool dependencies aren't compiled into the server.
- It reports "No vulnerabilities found" for the current code.
- With `go.mod` lowered to Go 1.27.0 and run with that toolchain, it reports
  several `net/http` vulnerabilities fixed in Go 1.27.2 and 1.27.4, and exits
  with status 3. So it does catch an outdated Go.

The version is in `go.mod` and `go.sum` rather than in the workflow, so that
a local `make vuln` and CI run the same version, and so that Dependabot can
update it (with the 14-day cooldown).

- Rejected: [`golang/govulncheck-action`](https://github.com/golang/govulncheck-action),
  which installs `govulncheck` itself. Its `govulncheck` version would be
  an input in the workflow, which Dependabot doesn't update (the same
  problem as golangci-lint's `version` in lafeingcrokodil/flashcards#44).
- Rejected: `go run golang.org/x/vuln/cmd/govulncheck@v1.9.0` in the
  Makefile, for the same reason.

🔴 **Whether Dependabot updates it:** a tool dependency is listed as
`// indirect` in `go.mod`, and Dependabot's run log showed that it only
updates direct dependencies by default. GitHub's docs don't say whether an
`// indirect` entry for a tool counts as direct. So `.github/dependabot.yml`
gets an explicit `allow` rule for it, next to the default:

```yaml
    allow:
      - dependency-type: direct
      - dependency-name: golang.org/x/vuln
```

This only becomes certain after merging: Dependabot re-runs when its
configuration changes, and its log should then show it checking
`golang.org/x/vuln` (and holding v1.10.0, published 2026-11-17, back for the
cooldown). That goes in the PR's "After merging" list.

### Where it runs

- **A `make vuln` target** running `go tool govulncheck ./...`, so that it can
  be run locally like the other checks.
- **A new workflow, `.github/workflows/vuln.yml`**, with one job,
  `govulncheck`: checkout, setup-go (version from `go.mod`, as in CI), and
  `make vuln`. The same pinned action SHAs as `ci.yml`, and `contents: read`.
  Its triggers are those of `ci.yml` (pull requests and pushes to `main`) plus
  a schedule.
  - Rejected: a job in `ci.yml`, which would need the schedule too. Then
    either `test` and `lint` would also run on the schedule for nothing, or
    each would need a condition to skip it.
- 🟡 **Daily at a fixed time, on `main`:** new vulnerabilities are published
  at any time, and a run takes well under a minute. When a scheduled run
  fails, GitHub notifies the user who created the workflow (you, since the
  commits are pushed with your account), if your notification settings
  include failed workflow runs. The next PR fails too, so the problem
  surfaces either way.
  - Rejected for now: opening an issue from the scheduled run. It needs
    `issues: write` permission and some scripting, which
    lafeingcrokodil/flashcards#44 will need anyway, so it's better built
    once there and then reused here.
  - GitHub [disables scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
    in public repositories, like this one, after 60 days without activity
    on the repository. If that happens, the PR and push
    runs still work, and the schedule can be turned back on in the Actions
    tab.

### 🟡 A required check

`govulncheck` is added to the `main` ruleset's required checks, like `test`
and `lint`. That means a PR can't be merged while `govulncheck` reports a
vulnerability, even one that isn't caused by the PR (for example, a newly
published one in the standard library). That's usually fixed by bumping Go or
a dependency, which is its own small PR. If something urgent needs to go in
first, you'd remove the requirement temporarily or bypass the ruleset.

- Rejected: not required, which would show the failure without blocking
  anything. That's easy to ignore, which is the problem this check is meant
  to fix.

### Documentation

The README's list of Make targets and its sentence on CI mention `make vuln`
and the new workflow.

## Risks

- **`govulncheck` passes when it shouldn't** (e.g. it isn't actually run, or
  runs on the wrong packages): the PR's CI log shows its output. To check
  that a finding fails the job, I'll push a temporary commit that lowers
  `go.mod` to Go 1.27.0, see `govulncheck` fail on the `net/http`
  vulnerabilities, and revert it.
- 🔴 **Dependabot doesn't update `golang.org/x/vuln`:** see "Design". Checked
  after merging, in the log of Dependabot's next run.
- **The `allow` rule changes what else Dependabot updates:** the first rule
  restates the default (direct dependencies), so nothing else should change.
  The same log after merging shows which dependencies it checked.
- **The workflow gets more permissions than it needs:** `contents: read`,
  visible in the YAML.
- **A new vulnerability blocks an unrelated urgent PR:** accepted (see "A
  required check").
- **The scheduled run stops without anyone noticing** (disabled after 60
  days without activity): not caught by any check. Low harm, since the PR
  and push runs continue.

## Close review

- 🔴 **New dependencies** in `go.mod` and `go.sum`: `golang.org/x/vuln` v1.9.0
  and the five `golang.org/x/...` modules it brings in. They're only used to
  run `govulncheck`, not compiled into the server.
- **`.github/workflows/vuln.yml`:** its triggers (including the schedule),
  permissions and action SHAs.
- 🔴 **The `allow` rule in `.github/dependabot.yml`:** a mistake there could
  stop Dependabot updating other dependencies, without any check noticing.
- **The `main` ruleset:** adding `govulncheck` as a required check is done by
  hand in the settings.
