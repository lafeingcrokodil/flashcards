# Issues from scheduled checks

Part of lafeingcrokodil/flashcards#44.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

Let a scheduled workflow report a problem as a GitHub issue, and use that
for the daily `govulncheck` run (`.github/workflows/vuln.yml`), which
currently only fails and sends a notification.

lafeingcrokodil/flashcards#44 is split in two, since together they'd make a
large PR:

1. **This PR:** a reusable "report as an issue" script, used by the daily
   `govulncheck` run.
2. **The next PR:** the monthly check for newer Go and golangci-lint
   versions, which reports through the same script. It gets its own plan,
   and closes #44.

Once this plan is approved, I'll open an issue in M0 for this part, so that
this PR has an issue to close, and narrow #44's description to the version
check.

## Design

### How a report works

A report has a fixed title, such as "govulncheck failed on main" (which also
covers errors, such as the vulnerability database being unreachable), and a
body: the problem's details, or nothing if there's no problem.
Given those, the script makes the repository's issues match:

| Problem found? | Open issue with that title? | Then |
| --- | --- | --- |
| Yes | No | Open one, with the `automated` label, assigned to the repository owner |
| Yes | Yes | Replace its description with the new details, if they changed |
| No | Yes | Close it, with a comment saying the check passes again |
| No | No | Nothing |

So a vulnerability that stays unfixed for a week is one issue, updated as
needed, not seven. Replacing the description rather than adding a comment
each day keeps the issue short, and the issue's edit history still shows
earlier versions.

🟡 **Closing automatically** when the check passes again means an issue
doesn't stay open after the problem is gone, for example once a Dependabot PR
or a Go update has fixed a vulnerability.

- Rejected: leaving issues open for you to close. That's one more thing to
  do by hand, and an issue that's no longer true is easy to mistake for an
  open problem.

🟡 **A new `automated` label** rather than `follow-up`, which `AGENTS.md`
reserves for your tasks after a PR. Both kinds are assigned to you, so they
appear together in your list either way. `AGENTS.md` gets a line about the
label.

### 🟡 A script for `actions/github-script`

The logic lives in one file, `.github/scripts/report-issue.js`, which exports
a function taking the title and body. A workflow step runs it with
[`actions/github-script`](https://github.com/actions/github-script), GitHub's
own action for running JavaScript with an authenticated API client:

```yaml
- uses: actions/github-script@3a2844b7e9c422d3c10d287c895573f7108da1b3 # v9.0.0
  with:
    script: |
      const report = require('./.github/scripts/report-issue.js')
      await report({github, context, title: '...', body: process.env.BODY})
```

v9.0.0 was released on 2026-04-09. The script is about 30 lines: list open
issues with the `automated` label, find the one with exactly the given title,
then open, edit or close it according to the table above. Keeping it in a
file rather than inline in the YAML means the version check (the next PR) can
use the same script.

This is less code of our own than any other option, and uses no third-party
dependency. The cost is that the script has no tests or linting (until the
front end brings ESLint, which could cover it). That's accepted, because a
bug can do little harm and is easy to undo: each run makes at most one write
(opening, editing or closing one issue), at most once a day. Instead, it's
tested end to end against the real API after merging (see "Risks").

- Rejected: a Go command (`internal/report` and `cmd/report-issue`), tested
  against a fake GitHub API. It would be the only option with tests, linting
  and the coverage check, but it's several times as much code for logic this
  small.
- Rejected: a shell script with the `gh` CLI. About as short, but no better
  tested, and quoting the issue body safely in shell is fiddly.
- Rejected: third-party actions. None of the ones I found covers the whole
  table, and in particular closing an issue once the problem is gone:
  - [`JasonEtco/create-an-issue`](https://github.com/JasonEtco/create-an-issue)
    creates an issue from a template file, and with `update_existing` updates
    an open issue with exactly the same title. It can't close one. Its last
    release, v2.9.2, is from 2024-02-15, and it still runs on Node 20, while
    the others here have moved to Node 24.
  - [`micalevisk/last-issue-action`](https://github.com/micalevisk/last-issue-action)
    (finds the last issue with given labels) together with
    [`peter-evans/create-issue-from-file`](https://github.com/peter-evans/create-issue-from-file)
    (creates an issue, or updates one given its number). Both are maintained
    (releases in 2026-09 and 2025-10), but it's two dependencies, and closing
    would still need a third step.

  A third-party action would also run with the job's `issues: write` token,
  so a compromised release could edit or spam issues. Pinning by SHA and the
  14-day cooldown limit that, but don't remove it.

### In `vuln.yml`

- **The `govulncheck` job** runs `make vuln` as before, and fails if it does,
  so that pull requests and pushes are blocked as before. It also passes the
  output on as a job output.
- **A new `report` job** runs after it, on scheduled and manual runs only,
  whether `govulncheck` passed or failed (but not if it was cancelled or
  skipped, since then there's no result). It runs the script with
  `govulncheck`'s output as the body if it failed, and with an empty body if
  it passed, so that a fixed issue gets closed. On a manual run, the optional
  input (see "Risks") replaces the output. The body links to the workflow
  rather than to the run, so that it doesn't change every day while the
  problem lasts.
- On pull requests and pushes, `report` is skipped, so they never touch
  issues.
- 🔴 **Permissions:** `issues: write` is granted to the `report` job only,
  which only checks out the repository and runs the script. The `govulncheck`
  job, which runs the Go toolchain and the code's dependencies, keeps
  `contents: read`. A pull request from a fork never gets a write token, and
  `report` doesn't run on pull requests anyway.

## Risks

- **The script opens duplicate issues, or edits or closes the wrong one:**
  no automated test. Issues are matched by exact title and the `automated`
  label, so an issue you opened yourself is never touched. Checked after
  merging with manual runs (`workflow_dispatch`, added to `vuln.yml` for
  this), which take an optional input that's reported instead of
  `govulncheck`'s output:
  1. With the input: an issue is opened.
  2. With a different input: the same issue's description is replaced.
  3. Without the input (and no vulnerabilities): the issue is closed.

  That covers every row of the table against the real API, and goes in the
  PR's "After merging" list. The input stays, so the same check can be
  repeated whenever the script changes.
- **The report step hides a `govulncheck` failure** (e.g. the job passes
  because the report step succeeded): the `govulncheck` step's own exit status
  still fails the job. Checked with a temporary commit lowering Go to 1.27.0,
  as in lafeingcrokodil/flashcards#85, on a pull request, where the report
  step doesn't run.
- 🔴 **A bug opens or edits issues repeatedly:** each run makes at most one
  write (open, edit or close one issue), and only once a day. Worst case is
  one noisy issue, which is easy to undo.

## Close review

- 🔴 **`.github/workflows/vuln.yml`:** the `issues: write` permission, and
  that the `report` job only runs on the schedule and on manual runs.
- **`.github/scripts/report-issue.js`:** the matching rules (exact title and
  label) that decide which issue is edited or closed, since nothing tests
  them before merging.
