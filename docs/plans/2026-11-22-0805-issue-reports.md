# Issues from scheduled checks

Part of lafeingcrokodil/flashcards#44.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

Let a scheduled workflow report a problem as a GitHub issue, and use that
for the daily `govulncheck` run (`.github/workflows/vuln.yml`), which
currently only fails and sends a notification.

lafeingcrokodil/flashcards#44 is split in two, since together they'd make a
large PR:

1. **This PR:** a reusable "report as an issue" command, used by the daily
   `govulncheck` run.
2. **The next PR:** the monthly check for newer Go and golangci-lint
   versions, which reports through the same command. It gets its own plan,
   and closes #44.

Once this plan is approved, I'll open an issue in M0 for this part, so that
this PR has an issue to close, and narrow #44's description to the version
check.

## Design

### How a report works

A report has a fixed title, such as "govulncheck found vulnerabilities on
main", and a body: the problem's details, or nothing if there's no problem.
Given those, the command makes the repository's issues match:

| Problem found? | Open issue with that title? | Then |
| --- | --- | --- |
| Yes | No | Open one, with the `automated` label, assigned to the repository owner |
| Yes | Yes | Replace its description with the new details, if they changed |
| No | Yes | Close it, with a comment saying the check passes again |
| No | No | Nothing |

So a vulnerability that stays unfixed for a week is one issue, updated as
needed, not seven. Replacing the description rather than adding a comment
each day keeps the issue short, and the issue's edit history still shows
earlier versions.

🟡 **Closing automatically** when the check passes again means an issue
doesn't stay open after the problem is gone, for example once a Dependabot PR
or a Go update has fixed a vulnerability.

- Rejected: leaving issues open for you to close. That's one more thing to
  do by hand, and an issue that's no longer true is easy to mistake for an
  open problem.

🟡 **A new `automated` label** rather than `follow-up`, which `AGENTS.md`
reserves for your tasks after a PR. Both kinds are assigned to you, so they
appear together in your list either way. `AGENTS.md` gets a line about the
label.

### A Go command, `cmd/report-issue`

The logic (finding the issue, deciding what to do, calling GitHub's REST
API) lives in `internal/report`, with a small command in `cmd/report-issue`
that reads the body from stdin:

```bash
make vuln 2>&1 | go run ./cmd/report-issue -title "govulncheck found vulnerabilities on main"
```

It uses the workflow's `GITHUB_TOKEN` and the `GITHUB_REPOSITORY` and
`GITHUB_REPOSITORY_OWNER` variables that GitHub Actions sets.

🟡 **Go rather than a shell script with the `gh` CLI**, because the decision
table above is easy to get subtly wrong (two issues for one problem, or none),
and in Go it's covered by tests, the linters and the coverage check like the
rest of the code. The tests run against a fake GitHub API (`httptest`), so
they need no network or token.

- Rejected: a shell script with `gh`. Shorter, but nothing would test it,
  and a mistake would only show up as wrong issues.
- Rejected: existing actions. None of the ones I found covers the whole
  table above, and in particular closing an issue once the problem is gone:
  - [`JasonEtco/create-an-issue`](https://github.com/JasonEtco/create-an-issue)
    creates an issue from a template file, and with `update_existing` updates
    an open issue with exactly the same title. It can't close one. Its last
    release, v2.9.2, is from 2024-02-15, and it still runs on Node 20, while
    the others below have moved to Node 24.
  - [`micalevisk/last-issue-action`](https://github.com/micalevisk/last-issue-action)
    (finds the last issue with given labels) together with
    [`peter-evans/create-issue-from-file`](https://github.com/peter-evans/create-issue-from-file)
    (creates an issue, or updates one given its number). Both are maintained
    (releases in 2026-09 and 2025-10), but it's two dependencies, and closing
    would still need a third step.
  - [`actions/github-script`](https://github.com/actions/github-script) is
    GitHub's own: it runs a JavaScript snippet with an authenticated API
    client, so it could do the whole table. It's not a third-party
    dependency, but the snippet would live inside the workflow's YAML,
    without tests or linting, which is the same problem as a shell script.

  Any third-party action would also run with this job's `issues: write`
  token, so a compromised release could edit or spam issues. Pinning by SHA
  and the 14-day cooldown limit that, but don't remove it.

It only uses the standard library (`net/http`, `encoding/json`), so it adds
no dependency.

### In `vuln.yml`

- The job runs `make vuln` and saves its output, as now. Its exit status
  still decides whether the job fails, so that PRs and pushes are blocked as
  before.
- On scheduled runs only, an extra step then runs `report-issue` with the
  output if `govulncheck` found something, and with an empty body if it
  didn't, so that a fixed issue gets closed. This step runs even when the
  `govulncheck` step failed (`if: always()` combined with the event check).
- On pull requests and pushes, there's no report step, so they never touch
  issues.
- 🔴 **Permissions:** the workflow needs `issues: write`, but only that one
  job, and only for the report step's token. The rest stays `contents: read`.
  A pull request from a fork never gets a write token, and the report step
  doesn't run on pull requests anyway.

## Risks

- **The command opens duplicate issues or closes the wrong one:** covered by
  table-driven tests of each row in the table above, against a fake API that
  records the requests. Issues are matched by exact title and the `automated`
  label, so an issue you opened with a similar title is left alone (also a
  test).
- **It works in tests but not against GitHub** (e.g. a wrong API path or
  permission): no check before merging, since the report step only runs on
  the schedule. After merging, I'd run it once by hand via `workflow_dispatch`
  (added to `vuln.yml` for that) and check that, with no vulnerabilities, it
  does nothing. Testing the "open an issue" path for real would need a real
  vulnerability, so that's left to the tests.
- **The report step hides a `govulncheck` failure** (e.g. the job passes
  because the report step succeeded): the `govulncheck` step's own exit status
  still fails the job. Checked with a temporary commit lowering Go to 1.27.0,
  as in lafeingcrokodil/flashcards#85, on a pull request, where the report
  step doesn't run.
- 🔴 **A bug opens or edits issues repeatedly:** each run makes at most one
  write (open, edit or close one issue), and only once a day. Worst case is
  one noisy issue, which is easy to undo.

## Close review

- 🔴 **`.github/workflows/vuln.yml`:** the `issues: write` permission, and
  that the report step only runs on the schedule and on manual runs.
- **`internal/report`:** the matching rules (exact title and label) that
  decide which issue is edited or closed.
