# Monthly check for newer Go and golangci-lint versions

For lafeingcrokodil/flashcards#44.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

Dependabot doesn't update two versions: Go (the `go` directive in `go.mod`)
and golangci-lint (the `version` of the `lint` job in
`.github/workflows/ci.yml`, also mentioned in the README). A monthly check
opens an issue when either is behind the newest release that's at least 14
days old, and closes it once it's up to date again, using the reporting from
lafeingcrokodil/flashcards#88.

Left for later: updating the versions automatically (the issue says what to
change, and the update is a small PR).

## Design

### What's compared

| Tool | Current version from | Newest release from |
| --- | --- | --- |
| Go | `go.mod`'s `go` directive (`1.27.4`) | the stable releases on `https://go.dev/dl/?mode=json`, with their dates from the Go module proxy (`golang.org/toolchain`) |
| golangci-lint | the `version:` of the `golangci-lint-action` step in `ci.yml` (`v2.15.0`) | the versions of `github.com/golangci/golangci-lint/v2` on the Go module proxy, with their dates |

For each tool, the check takes the newest release that's at least 14 days
old (pre-releases excluded) and compares it with the current version. If the
README's golangci-lint version differs from `ci.yml`'s, that's reported too,
since the README would then tell people to install the wrong version.

Today both are up to date: Go 1.27.4 was released on 2026-11-02, and
golangci-lint v2.15.0 on 2026-10-16, with nothing newer.

🟡 **The module proxy for golangci-lint's dates** rather than GitHub's
releases API. The proxy records when it first saw each version, which is
usually close to the release (I haven't verified how close), and it's the
same source as Go's dates, so there's one way of getting dates instead of
two.

- Rejected: GitHub's releases API (`published_at`). Equally good in the
  workflow, but I couldn't try it from this environment, whose GitHub access
  is limited to this repository.

### 🟡 One issue per tool

Two reports: "Go is out of date" and "golangci-lint is out of date", each
with the current version, the newest eligible one, its release date, and
which files to change. Updating one tool then closes its issue without
waiting for the other.

- Rejected: one issue for both, which would stay open until both are
  updated and would need its description rewritten when only one is.

### Where it runs

- **A new workflow, `.github/workflows/versions.yml`**, with one job: check
  out the repository, then run `.github/scripts/check-versions.js` with
  `actions/github-script` (the same pinned SHA as `vuln.yml`), which reads
  the files, fetches the releases, and calls `report-issue.js` once per tool.
- **Monthly, on the 3rd at 06:41 UTC**, plus manual runs
  (`workflow_dispatch`). The minute isn't 0, for the same reason as in
  `vuln.yml`.
- **Permissions:** `contents: read` and `issues: write`. Unlike `vuln.yml`,
  there's nothing to separate: the job runs no code from the repository's
  dependencies, only the checkout and the two scripts.

### Testing

Like `report-issue.js`, `check-versions.js` has no committed tests, as agreed
for #88. Instead:

- Before merging, I'll run its comparison logic locally against fake inputs
  (an older Go, a newer release that's under 14 days old, a pre-release, a
  README that disagrees with `ci.yml`), as I did for `report-issue.js`.
- 🟡 After merging, manual runs test it end to end. Since both tools are up
  to date today, a manual run takes optional inputs that replace the current
  versions it reads (e.g. Go `1.27.0`), so that a run can be made to find
  something:
  1. With Go set to `1.27.0`: "Go is out of date" is opened.
  2. Without inputs: it's closed again.

  That goes in the PR's "After merging" list.

## Risks

- **A version is compared wrongly** (e.g. `1.27.10` treated as older than
  `1.27.4`, or a release candidate counted as stable): numeric comparison of
  each part, and pre-releases excluded: go.dev's list has a `stable` flag,
  and the proxy's pre-release versions have a suffix after `-`. Covered
  by the local check with fake inputs before merging, not by a committed test.
- **The check reads the wrong version from a file** (e.g. after `ci.yml` is
  restructured): if it can't find a version, the run fails instead of
  reporting "up to date", so it doesn't go quiet. A failed scheduled run
  sends a notification, as for `vuln.yml` before #88.
- **go.dev or the module proxy is unreachable or changes its format:** the
  run fails rather than reporting anything, as above.
- **The scheduled run stops** (GitHub disables schedules in public
  repositories after 60 days without activity): low harm, since it's a
  reminder. It can be turned back on in the Actions tab.

## Close review

- **`.github/workflows/versions.yml`:** its `issues: write` permission and
  schedule.
- None of the rest needs more than a skim: a wrong comparison or a missed
  version only means a wrong or missing reminder, which is easy to fix and
  does little harm.
