# SvelteKit + TypeScript app scaffold, with linting in CI

For lafeingcrokodil/flashcards#46.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

Add the front end's skeleton in `web/`: a SvelteKit + TypeScript app, built as
a single-page app with `adapter-static`, that shows a placeholder page. CI
type-checks, lints and builds it on every pull request and push to `main`, and
Dependabot keeps its dependencies up to date.

Left for later:

- Serving the built app from the Go binary, and running the dev server against
  the Go server (lafeingcrokodil/flashcards#47), so the Makefile doesn't change
  here.
- The Dockerfile (lafeingcrokodil/flashcards#48) and sign-in
  (lafeingcrokodil/flashcards#59).
- Styles, a favicon and anything else that a real page needs: they come with
  the first real page.

## Design

### Layout: like diary's `web/`

The files are diary's `web/`, without what belongs to its features (sign-in,
the API client, styles, pages):

| File | What it's for |
| --- | --- |
| `package.json` | scripts (`dev`, `build`, `preview`, `check`, `lint`, `format`), dev dependencies, `packageManager: pnpm@12.18.0`, `engines.node >=26`, and the `#lib` import alias |
| `pnpm-lock.yaml` | the locked versions |
| `pnpm-workspace.yaml` | `minimumReleaseAge: 20160` (14 days, in minutes), so that pnpm refuses newer versions |
| `.npmrc` | `engine-strict=true`, so that an older Node fails the install |
| `.nvmrc` | the Node version for CI and local development |
| `vite.config.ts` | the SvelteKit plugin (runes mode, `adapter-static` with an `index.html` fallback, so that routing happens in the browser) |
| `tsconfig.json`, `src/app.d.ts` | as SvelteKit generates them |
| `src/app.html` | as SvelteKit generates it, plus `<meta name="color-scheme" content="light dark">`, so that the unstyled page follows the system's dark mode |
| `src/routes/+layout.ts` | `ssr = false`, so that the app can be served as static files |
| `src/routes/+page.svelte` | a placeholder: the app's name and a one-line description |
| `src/lib/index.ts` | the `#lib` alias's target, empty for now |
| `static/robots.txt` | disallows everything, since it's a personal app |
| `eslint.config.js`, `prettier.config.js`, `.prettierignore` | see "Linting" |
| `.gitignore`, `.vscode/extensions.json`, `README.md` | as in diary |

Versions: each dependency's range is diary's, and pnpm resolved the newest
versions that are at least 14 days old (e.g. `@sveltejs/kit` 3.1.1, `svelte`
5.57.3, `vite` 8.3.6, `typescript` 6.0.3, `eslint` 10.14.0). I checked every
package in the lockfile against the npm registry: the newest of the 205 was
published on 2026-11-08. pnpm 12.18.0 was published on 2026-11-05.

- Rejected: generating the app with `sv create`. It would add things that
  diary has removed or replaced (e.g. a `svelte.config.js`), which would then
  have to be removed again.

### 🟡 Node: pinned to an exact version

`.nvmrc` says `26.13.0` (the current LTS release, published 2026-10-28), not
diary's `26`. With just `26`, `actions/setup-node` installs the newest 26.x on
every run, which can be days old, against the 14-day rule in `AGENTS.md`. The
cost is that it has to be bumped by hand, since Dependabot doesn't update
`.nvmrc` (see "Dependabot").

- Rejected: `26`, as in diary, which never needs bumping but breaks the
  14-day rule.

### Linting: every rule, as in diary

`pnpm lint` runs `prettier --check .` and `eslint .`, and `pnpm check` runs
`svelte-check` (TypeScript, including in `.svelte` files). The ESLint
configuration is diary's: `js.configs.all`, `ts.configs.all` (type-aware) and
`svelte.configs.all`, with diary's disabled rules and their reasons. Two of
its settings are left out because nothing here uses them yet: the
`svelte/no-unused-class-name` allowlist of global CSS classes (there's no
global stylesheet), and the relaxed length rules for test files (there are no
tests).

### 🟡 No Vitest yet

diary runs Vitest, but there's no TypeScript logic here to test yet, and
Vitest fails when it finds no test files. So `pnpm test`, Vitest and its CI
step come with the first code that needs tests.

- Rejected: Vitest now, with `passWithNoTests`. That option would then have to
  be removed again, or a test file that's missing later (e.g. because of a
  wrong `include` pattern) would pass silently.

### CI: a `web` job in `ci.yml`

As in diary, a `web` job runs in `web/`:

1. `actions/checkout` (the same SHA as the other jobs)
2. `pnpm/action-setup` v6.1.1 (2026-11-03), pinned by SHA, which installs the
   pnpm version from `packageManager`
3. `actions/setup-node` v7.1.0 (2026-10-07), pinned by SHA, with the Node
   version from `.nvmrc` and pnpm's store cached by the lockfile's hash
4. `pnpm install --frozen-lockfile`, so that CI fails if the lockfile doesn't
   match `package.json`
5. `pnpm check`, `pnpm lint` and `pnpm build`

The actions are pinned by SHA, like this repository's other actions, unlike
diary's (which uses tags). The workflow keeps `contents: read`.

🟡 **A required check:** `web` is added to the `main` ruleset's required
checks, like `test`, `lint` and `govulncheck`, by hand in the settings.

### Dependabot

A new `npm` entry (pnpm uses npm's ecosystem) for `/web`, monthly, with the
14-day cooldown and minor and patch updates grouped, as in diary.

Dependabot doesn't update `.nvmrc`, and I couldn't confirm whether it updates
the pnpm version in `packageManager`. Rather than handle them here, I'll open
an issue to add Node and pnpm to the monthly version check
(`.github/workflows/versions.yml`), which already does this for Go and
golangci-lint.

### Documentation

- `web/README.md`: what the front end is, its requirements (the Node version
  in `.nvmrc`, the pnpm version in `packageManager`) and its `pnpm` commands.
- The root README: a pointer to `web/README.md`, and the table of automated
  checks mentions the new CI step.

## Risks

- **ESLint doesn't actually lint the `.svelte` files** (e.g. a wrong parser
  setting), so lint passes when it shouldn't: tried locally, a `.svelte` file
  with an unused class and a `let` that's never reassigned fails `eslint .`.
  To check it in CI too, I'll push a temporary commit with such a file, see
  the `web` job fail, and revert it.
- **A dependency younger than 14 days gets in:** pnpm refuses them while
  resolving (`minimumReleaseAge`), and I checked the lockfile against the
  registry (see "Layout"). Dependabot's updates respect the same limit
  through its cooldown. Neither is a check in CI: a hand-edited lockfile
  could get past them.
- 🔴 **Dependabot doesn't pick up the `npm` entry**, or doesn't update pnpm
  dependencies correctly: checked after merging, in the log of Dependabot's
  next run.
- **The build succeeds but produces an unusable app:** not checked by CI until
  lafeingcrokodil/flashcards#47 serves it. Low harm, since nothing serves it
  yet. I'll check the built `index.html` locally with `pnpm preview`.
- **The workflow gets more permissions than it needs:** `contents: read`,
  visible in the YAML.

## Close review

- 🔴 **New dependencies** in `web/package.json` and `web/pnpm-lock.yaml`: all
  dev dependencies, the same set as diary's minus Vitest. Only `svelte` and
  `@sveltejs/kit` end up in the built app.
- **The `web` job in `.github/workflows/ci.yml`:** its two new actions and
