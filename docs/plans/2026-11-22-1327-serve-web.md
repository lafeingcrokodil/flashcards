# Serve the front end from the Go binary, and a local dev setup

For lafeingcrokodil/flashcards#47.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

The Go binary embeds the built front end (`web/build/`) and serves it, so that
the whole app is one binary. For local development, `make run` builds the front
end and runs the server on http://localhost:8080, and for instant reloading,
Vite's dev server (`pnpm dev`) forwards API requests to the Go server.

Left for later:

- The Dockerfile, and a CI check that the image serves the app
  (lafeingcrokodil/flashcards#48).
- The API itself: there are no API routes yet, only the `/api/` prefix that
  they'll live under (see "Routes").

## Design

Mostly as in diary. The departures are marked in the headings.

### Embedding: a `web` Go package in `web/`

`web/web.go` (package `web`) embeds `web/build` with `//go:embed all:build`,
and `web.Build()` returns it as an `fs.FS` rooted at the build directory. The
`all:` prefix is needed because SvelteKit puts its assets in `_app/`, and
`go:embed` skips names starting with `_` or `.` without it.

`cmd/flashcards` passes those files to `server.New`, which takes an `fs.FS`
rather than embedding the files itself, so that the tests can use a small
`fstest.MapFS` instead of the real build.

- Rejected: embedding in `cmd/flashcards` or `internal/server`. `go:embed`
  can only embed files in the package's directory or below it, so the package
  has to be in `web/` or above it.

### Placeholder: so the Go code compiles without a front-end build

`go:embed` fails to compile if `web/build` doesn't exist, and it's ignored by
Git. As in diary, a Makefile rule creates a placeholder `web/build/index.html`
("The front end has not been built. Run make web.") if there's no build, and
`make test`, `cover`, `vet`, `lint` and `vuln` depend on it, so that the Go
checks don't need Node. CI's `test` job and the Vulnerabilities workflow run
those targets, so they get the placeholder without changes. The `lint` job
runs golangci-lint through its action rather than `make lint`, so it gets a
`make web/build/index.html` step first.

`make build` and `make run` depend on a new `make web` instead, which runs
`pnpm install --frozen-lockfile && pnpm build` in `web/`, so a binary built
with them always has the real front end.

- Rejected: committing a placeholder in `web/build/`. `pnpm build` replaces the
  directory, so the committed file would show up as deleted in `git status`
  after every build.

### Routes

| Route | Response |
| --- | --- |
| `GET /health` | `ok`, as now |
| `/api/...` | 404, for now (see below) |
| an existing file (e.g. `/_app/immutable/entry/app.js`, `/robots.txt`) | the file |
| a missing path with a file extension (e.g. an outdated script) | 404 |
| any other path (e.g. `/`, `/packs/123`, a directory) | `index.html`, so that the app handles the route in the browser |
| a front-end path with a method other than `GET` or `HEAD` | 405 |

The front-end handler is diary's `handleFrontend`. Unknown paths that used to
get a 404 now get `index.html` with a 200, so the existing test case for them
changes.

🟡 **`/api/` reserved now:** diary only adds `/api/` with its first API route.
Here it's added now, as a 404 handler that the API's own mux will replace, so
that an API request to the Go server never gets `index.html` (with a 200)
instead of an error, and so that the dev server's proxy (see below) has
something to forward to.

- Rejected: leaving it to the first API route, as in diary. Until then, the
  proxy would only forward requests to a page that the dev server serves
  anyway.

### 🟡 Departure: long-lived caching for SvelteKit's hashed assets

diary serves every file without caching headers. Since embedded files have no
modification time, `http.FileServerFS` can't send `Last-Modified` either, so
browsers download every script and stylesheet again on each page load.

Files under `/_app/immutable/` get `Cache-Control: public, max-age=31536000,
immutable`. SvelteKit puts only content-hashed files there (a changed file gets
a new name), so a browser can keep them for a year. Everything else
(`index.html`, `robots.txt`, `/_app/version.json`, ...) keeps the current
behaviour: no caching headers, so the browser always fetches it again and picks
up a new deployment straight away.

- Rejected: no caching, as in diary. It works, but makes every page load
  download the whole app.
- Rejected: ETags (e.g. from a hash of each file). More code, and it doesn't
  save the request, only the download.

### Dev server: `/api` forwarded to the Go server

As in diary, `web/vite.config.ts` gets
`server.proxy: { '/api': 'http://localhost:8080' }`. Running `make run` and
`pnpm dev` side by side, http://localhost:5173 serves the front end with
instant reloading, and its API requests go to the Go server. diary's second
proxy (`/__`, for Firebase Hosting) comes with sign-in
(lafeingcrokodil/flashcards#59).

### Makefile and documentation

New `make help` entries:

- `web`: build the front end into `web/build/`
- `run`: build the front end and run the server (as now, but with the front end)
- `build`: build the front end and a binary that includes it

The root README describes the placeholder, the two ways of running the app
locally (`make run` on its own, or with `pnpm dev`), and that the Go targets
that build the front end need the requirements in `web/README.md`.
`web/README.md` says that `pnpm dev` forwards `/api` to the Go server.
`docs/architecture.md` already describes the embedding, so it doesn't change.

## Risks

- **The binary embeds the placeholder instead of the real front end:** only
  `make build` and `make run` build binaries here, and both build the front end
  first. The image (lafeingcrokodil/flashcards#48) will need the same, checked
  by that PR's image check.
- **The routes behave differently than in the table**, e.g. a missing script
  gets `index.html`, or `/api/...` gets the front end: covered by test cases
  for every row of the table, with a `fstest.MapFS`.
- 🔴 **A file that can change without changing its name gets the long-lived
  cache header**, so browsers keep an old version for up to a year, which
  can't be undone from the server. Covered by test cases that only paths under
  `/_app/immutable/` get it; whether SvelteKit only puts hashed files there is
  from its documentation, and I'll check the file names in the build.
- **The built app doesn't work when served by Go** (e.g. a wrong path to its
  assets): not covered by CI until lafeingcrokodil/flashcards#48. I'll check
  `make run` and `make build` in a browser, with screenshots in the PR.
- **The dev server's proxy doesn't forward:** I'll check that a request to
  http://localhost:5173/api/... gets the Go server's 404.
- **A Go check in CI fails because the placeholder is missing**: CI fails
  visibly, and I'll run each job's steps locally on a clean checkout.

## Close review

- 🔴 **The `Cache-Control` header for `/_app/immutable/`** (in
  `internal/server/server.go`): see the cache risk above.

The other parts come close but pass: the routes are covered by tests, a mistake
in the Makefile or in the `lint` job's new step fails CI, and the dev server
setup only affects local development and is easy to change.
