# Dockerfile, and a CI check that the image serves the app

For lafeingcrokodil/flashcards#48.

Markers: 🟡 a judgement call where you might prefer the alternative; 🔴
risky or uncertain.

## Goal

A `Dockerfile` that builds the whole app (the front end, and the Go binary
that embeds it) into a small image, and a CI job, `image`, that builds the
image, runs it and checks that it serves the app: `/health`, and the real
front end rather than the placeholder page. Until now, nothing in CI checks
that the built front end works when the Go binary serves it.

Left for later:

- Pushing the image to Artifact Registry and deploying it
  (lafeingcrokodil/flashcards#52, lafeingcrokodil/flashcards#53).

## Design

Mostly as in diary. The departures are marked in the headings.

### Dockerfile: three stages

| Stage | Base image | What it does |
| --- | --- | --- |
| `web` | `node:26.13.0-trixie-slim` | Installs pnpm (the version in `packageManager`) and the dependencies, then runs `pnpm build`. The manifests are copied before the sources, so that the install is cached while only the sources change. |
| `server` | `golang:1.27.4-trixie` | Downloads the modules, copies `cmd/`, `internal/`, `web/web.go` and the `web` stage's `build/`, and builds a static binary (`CGO_ENABLED=0`, `-trimpath`, `-ldflags="-s -w"`). |
| final | `gcr.io/distroless/static-debian13:nonroot` | Only the binary: no shell or package manager, and an unprivileged user. `EXPOSE 8080`, `ENTRYPOINT ["/flashcards"]`. |

The Node and Go versions are the ones in `web/.nvmrc` and `go.mod`, rather
than diary's (which are a patch behind). Each base image is pinned by digest
as well as tag, so that builds are reproducible.

A `.dockerignore` sends only what the build needs (`go.mod`, `go.sum`, `cmd/`,
`internal/`, `web/`), without `web/node_modules/`, `web/build/` and
`web/.svelte-kit/`. Excluding `web/build/` means a local placeholder or an
old build can never end up in the image: the `server` stage only gets the
`web` stage's build.

- Rejected: an Alpine-based build or final image. The binary is static, so
  distroless static has everything it needs and less than Alpine (no shell),
  and the build stages' base doesn't affect the final image.

### 🔴 Base images that are at least 14 days old

AGENTS.md asks for versions published at least 14 days ago, and for an image
that's the digest, since an official image's tag is rebuilt (e.g. for Debian
updates) without changing its name. Today:

| Image | Version released | Current digest pushed |
| --- | --- | --- |
| `node:26.13.0-trixie-slim` | | 2026-11-05 (17 days) ✅ |
| `golang:1.27.4-trixie` | Go 1.27.4: 2026-11-02 (20 days) | 2026-11-10 (12 days) ❌ |
| `gcr.io/distroless/static-debian13:nonroot` | | unknown: distroless images have no creation date |

When implementing, I'll pin the digest that each tag had at least 14 days
earlier, checked again on the day:

- `golang`: Docker Hub only shows a tag's current digest, so if it's still
  younger than 14 days, I'll wait until it isn't (2026-11-24 for the current
  one) rather than pin an older one I can't date.
- distroless: diary's digest (`25ac8f0…`), which diary has used since
  2026-11-01, so it's at least that old. It's no longer the tag's current
  digest (`aafe993…`, which I can't date), but it's still pullable, and
  Dependabot will propose the newer one once it's due.

- Rejected: the current digests regardless of age. Simpler, but against the
  14-day rule for `golang`, and unknown for distroless.

### 🟡 Departure: no `# syntax=docker/dockerfile:1` line

diary's Dockerfile starts with it, which makes BuildKit pull the newest
`docker/dockerfile:1` image on every build: an unpinned dependency that
changes without a commit. The Dockerfile only uses instructions that the
BuildKit built into Docker supports, so the line isn't needed.

- Rejected: keeping it with a pinned digest. It's one more image for
  Dependabot to update, for features that aren't used.

### 🟡 Departure: CI checks that the Dockerfile's versions match

The Go and Node versions appear twice: in `go.mod` and `web/.nvmrc`, and in
the Dockerfile's tags. Dependabot's `docker` updates (see below) bump the
Dockerfile only, and a Go update in `go.mod` doesn't touch the Dockerfile. The
`golang` image sets `GOTOOLCHAIN=local`, so an image older than `go.mod`
fails the build, but a newer one doesn't, and Node has no such check
(`engines` only asks for `>=26`).

So the `image` job starts with a step that compares the `golang` tag's version
with `go.mod`'s `go` line, and the `node` tag's version with `web/.nvmrc`, and
fails with a message saying which to update if they differ. A Dependabot PR
that bumps only the Dockerfile then fails CI until `go.mod` or `.nvmrc` is
bumped with it.

- Rejected: passing the versions in as build arguments. The digests can't be
  derived from them, so they'd still be in the Dockerfile.
- Rejected: no check, as in diary. The versions would drift apart unnoticed,
  so that CI tests with one Go version and the image is built with another.

### 🟡 Departure: the check tells the real front end from the placeholder

diary's `image` job checks `/health`, and that `/` contains `<html`. Here, as
the issue asks, the check has to fail for the placeholder page, which the Go
binary would serve if the image ever embedded it. So after `/health`, the job:

1. fetches `/` and checks that it references a script under
   `/_app/immutable/`, which the real `index.html` does and the placeholder
   doesn't, and
2. fetches that script and checks that it's served (HTTP 200), so that a wrong
   path to the assets fails too (the risk that lafeingcrokodil/flashcards#102
   left to this issue).

As in diary, the job starts the container with `docker run --detach
--publish 8080:8080`, retries `/health` for up to 5 seconds while the server
starts, and uses `curl --fail`. The server doesn't need any configuration yet,
so there are no `--env` flags. The job is in `ci.yml`, with `actions/checkout`
pinned by SHA like the other jobs, and the workflow's read-only permissions.

### Dependabot: base image updates

A `docker` entry in `.github/dependabot.yml`, as in diary: monthly, with the
14-day cooldown, and minor and patch updates grouped. It updates both the tags
and the digests. A digest-only update (a rebuilt tag) passes the version
check; a version update fails it until `go.mod` or `.nvmrc` is updated too
(see above).

### Makefile and documentation

- `make image`: builds the image as `flashcards`, as in diary. It needs only
  Docker.
- The root README mentions `make image`, and its "Automated checks" table
  says that `ci.yml` also builds and checks the image.
- `docs/architecture.md` already says that the app is a single container, so
  it doesn't change.

## Risks

- **The image embeds the placeholder, or its assets aren't served:** the
  `image` job's checks of `index.html` and of one of its scripts.
- **The Dockerfile's Go or Node version drifts from `go.mod` or
  `web/.nvmrc`:** the version check in the `image` job.
- **The version check doesn't fail when it should** (e.g. its parsing of the
  Dockerfile matches nothing and compares empty strings): I'll make it fail if
  either version can't be found, and try it locally with mismatched versions.
- **The image doesn't run on Cloud Run** (e.g. wrong architecture, or the
  port): not covered until deployment (lafeingcrokodil/flashcards#53). The
  image is `linux/amd64` (what GitHub's runners build), and the server already
  reads `PORT`.
- 🔴 **A base image digest is younger than 14 days, or compromised:** not
  covered by a check. See "Base images that are at least 14 days old"; the
  digests are what to compare.
- **The build is slow in CI:** no layer cache between runs, so every run
  installs the Node and Go dependencies. I'll note the job's time in the PR;
  caching can be added later if it's a problem.

## Close review

- 🔴 **The base image digests** in the `Dockerfile`: see the risk above. A
  wrong digest isn't caught by any check, and once deployed, it's what runs.

The other parts come close but pass: the new CI job only reads the
repository (the workflow's existing permissions) and pushes nothing, a broken
Dockerfile, `.dockerignore` or
image fails the `image` job, a wrong version check fails visibly (and is tried
with mismatched versions), and the Dependabot entry is checked once it's on
`main` (see the follow-ups in the PR).
